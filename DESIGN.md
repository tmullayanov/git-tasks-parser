# Проект CLI: коммиты Git и ключи задач в Excel

## Назначение

Утилита принимает один или несколько локальных Git-репозиториев, главную ветку
и часовой пояс отчёта. Она создаёт файл `.xlsx` с одним листом и пятью
столбцами:

| Commit hash | Issue key | author email | Commit date | repository name |
| --- | --- | --- | --- | --- |
| `a1b2…` | `PROJ-123` | `author@example.com` | `2026-10-28 09:30` | `project` |

Отчёт строится по **всем коммитам, достижимым из указанной главной
ветки**. Сюда входят коммиты, пришедшие через слияния. Коммиты из веток, ещё
не слитых в главную, в отчёт не попадают.

## Интерфейс команды

Предлагаемый вызов после упаковки проекта:

```text
git-tasks-parser --repo PATH [--repository-name NAME] [--repo PATH [--repository-name NAME] ...] --main-branch REF --timezone ZONE --output FILE.xlsx
```

Пример:

```text
git-tasks-parser --repo C:\work\project --main-branch main --timezone Europe/Moscow --output C:\reports\commits.xlsx
```

`--repo` можно повторять; все перечисленные репозитории попадут в **один**
файл. `--main-branch`, `--timezone` и `--output` обязательны и общие для
всего запуска. Для `--main-branch` короткое имя `main`
обозначает локальную ветку `refs/heads/main`; полное имя
`refs/remotes/origin/main` позволяет явно выбрать remote-tracking ветку.
Произвольные выражения ревизий и теги не принимаются. Утилита не выполняет
`fetch` и не меняет репозиторий, поэтому анализирует состояние выбранной
ссылки на момент запуска. Если файл результата существует, команда
завершается с ошибкой, чтобы случайно его не перезаписать.

`--repository-name` переопределяет имя **предшествующего** `--repo` и должен
стоять сразу после него. Если параметр для данного репозитория отсутствует,
имя берётся из директории. Так можно переименовать лишь некоторые
репозитории. Пустые и повторяющиеся без учёта регистра итоговые имена —
ошибка, поскольку пользователь должен различать строки по этому столбцу.

Пример общей выгрузки с явными именами:

```text
git-tasks-parser --repo C:\work\api --repository-name backend --repo C:\work\web --repository-name frontend --main-branch main --timezone Europe/Moscow --output C:\reports\all.xlsx
```

Этот интерфейс рассчитан на одинаковое имя главной ветки во всех выбранных
репозиториях. Если оно различается, следующим расширением будет файл-манифест
с отдельными `path`, `branch` и `name` для каждого репозитория.

## Правила построения таблицы

1. Для каждого `--repo` проверить, что путь указывает на доступный
   Git-репозиторий, а заданная ветка существует и указывает на коммит. Работа
   на detached HEAD допустима: текущая checkout-ветка не влияет на результат.
2. Перечислить каждый достижимый из ветки коммит ровно один раз, включая
   merge-коммиты. Порядок — топологический, от потомков к предкам. Это не
   обещает строгой сортировки по дате при параллельной истории.
3. Для каждого коммита взять полный hash, **author email**, **committer date**
   и текст сообщения. Email коммитера (`committer`) не подменяет email автора;
   email берётся как записано в коммите, без `.mailmap`. `Commit date` — дата
   создания данного объекта коммита. Время автора (`author date`) может
   отличаться, например после rebase.
4. Из полного сообщения коммита извлечь уникальные ключи формата
   `PROJECT-123`. При поиске требовать **верхний регистр**: Jira хранит
   project key прописными латинскими буквами. Базовый шаблон: не менее двух
   символов в project key, первый — буква, последующие — буквы, цифры или
   подчёркивания; затем дефис и положительное число. Вхождения внутри более
   длинных слов не считать ключами. Регистр в Excel не менять. Строка
   `proj-123` в первой версии ключом не считается.
5. Если в сообщении несколько разных ключей, создать отдельную строку на
   каждую пару «коммит — ключ»; повторение одного ключа в том же сообщении
   не создаёт повторной строки. Если ключа нет, всё равно создать строку
   коммита с пустым полем `Issue key`. Это сохраняет полноту учёта коммитов.
6. Перевести дату каждого коммита в пояс `--timezone` и записать в
   `Commit date` локальные дату и время **без суффикса зоны** с отображением
   `YYYY-MM-DD HH:MM`. В книге хранить значение как дату/время Excel, чтобы
   его можно было сортировать и фильтровать. Секунды скрываются только при
   отображении: округлять до следующей минуты не нужно. Все остальные
   значения записывать как текст, чтобы метаданные Git не интерпретировались
   Excel как формула.
7. `repository name` заполнять итоговым именем данного репозитория: значением
   `--repository-name` либо последним компонентом нормализованного пути
   `--repo`. Регистр и написание имени не менять.
8. На единственном листе записать заголовки **точно** `Commit hash`,
   `Issue key`, `author email`, `Commit date`, `repository name`. Строки
   сгруппировать по порядку аргументов `--repo`; внутри каждого репозитория
   сохранить топологический порядок коммитов.

Часовой пояс задаётся именем IANA, например `Europe/Moscow` или
`Asia/Vladivostok`; он один для всей книги. Например, `11:30 +05:00` — это
`06:30 UTC`, значит в `Europe/Moscow` будет `09:30`, а в
`Asia/Vladivostok` — `16:30`. Исходное смещение не печатается в таблице.

Например, коммит с ключами `PROJ-123` и `OPS-7` даст две строки с одинаковыми
hash и email. Коммит без ключа даст одну строку с пустым вторым столбцом.

Сбой чтения любого репозитория или записи Excel завершает весь запуск с
ненулевым кодом и сообщением об ошибке; частично записанный файл не должен
оставаться на месте результата. Лимит строк Excel применяется к общей книге.

## Несколько репозиториев в одном файле

Основной путь — один запуск с повторённым `--repo`. Это естественное
расширение существующей команды: один проход по каждому репозиторию, одна
книга и одна атомарная запись результата. Совпавшие hash в разных
репозиториях **не** удаляются: строки различаются по `repository name`.

Альтернатива — запускать команду отдельно для каждого репозитория с
`--append` к тому же `.xlsx`. Тогда каждый запуск должен читать и переписывать
готовую книгу, проверять её схему и часовой пояс, а также решать, что делать
с повторными строками при повторном запуске. Это усложняет и ручную работу,
и реализацию. Поэтому `--append` пока не включён в проект.

При большом наборе репозиториев список путей можно сформировать внешним
скриптом и передать той же команде. Если понадобятся индивидуальные ветки
или дополнительные настройки, файл-манифест будет удобнее длинной команды.

## Почему пока не нужны все ветки

Анализ главной ветки уже включает историю веток, влитых обычным merge. При
squash-слиянии в ней остаётся только созданный squash-коммит: исходные
feature-коммиты не являются его предками. Обход **всех** веток
добавит прежде всего коммиты, которые ещё не вошли в главную, а также может
добавить историю экспериментальных или устаревших веток. Один коммит может
встречаться в нескольких ветках, поэтому объединённый отчёт всё равно должен
дедуплицировать коммиты по hash. По единственному hash нельзя однозначно
назначить «исходную» ветку: ссылки веток могут быть переименованы, удалены
или указывать на один и тот же коммит.

Если впоследствии понадобится отчёт по незавершённой работе, можно добавить
отдельный режим `--all-local-branches`. Его контракт надо будет определить
отдельно: включать ли remote-tracking ветки, как отмечать коммиты вне главной
ветки и как избежать устаревших ссылок. Для текущего формата отчёта
такой режим полезен только если важны ещё не слитые коммиты.

## Вопросы перед реализацией

- Уточнить, настроен ли в вашей Jira собственный формат project key. Для
  Jira Cloud разрешены прописные буквы и цифры; Jira Data Center допускает
  настройку формата, в том числе ключи с подчёркиванием. Без запроса к Jira
  совпадение с шаблоном подтверждает лишь форму, но не существование задачи.
- Решить, нужно ли в будущем распознавать ошибочно написанные строчными
  буквами ключи в сообщениях коммитов. Это увеличит число ложных совпадений
  с обычным текстом.
- При большой истории решить, нужен ли ограничитель периода или начального
  коммита. Текущий проект охватывает всю историю главной ветки. Формат `.xlsx`
  допускает не более 1 048 576 строк на лист; при превышении команда должна
  завершиться с ясной ошибкой.
- Для работы с именами поясов IANA на Windows понадобится доступная база
  часовых поясов; при реализации можно добавить зависимость `tzdata`.
